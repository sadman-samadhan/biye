# Phase 4 — Guest passcodes, root URLs & the phase engine

Base: `v2/p03-media` · Branch: `v2/p04-guest-access`

Each couple's link is now `shubhobiye.com/{slug}`. It is protected by a passcode they share with their invitation, and it knows whether it should currently be an invitation, the live day or the memories site.

## What changed

**Passcodes**
- Every new site gets a passcode like `shapla-4821` (flowers of Bengal + 4 digits). Sites created earlier get one the first time the couple opens *Privacy & sharing*.
- Stored AES-256-GCM encrypted (`site_access.passcode_enc`) so the couple can always see and share it. Guests' input is forgiving: case, spaces and Bangla digits (০–৯) don't matter. Comparison is constant-time.
- `POST /api/g/:slug/unlock {passcode, name?}` sets a signed per-site guest cookie (`shb_g_<site>`, 30 days, HS256 via `jose`) carrying the passcode version and optional guest name.
- Brute-force limits (failures only): 30 / 10 min per IP+site (generous because of mobile carrier NAT), 8 / 10 min per device, 300 / hour per site. While any limit is hit, *every* attempt is refused, so throttling can't confirm a guess.
- **Rotate passcode** or **Sign everyone out** bumps the version: all guest cookies and one-tap links stop working at once.

**One-tap links** — `/{slug}/u/{key}` (HMAC of site + passcode version) unlocks and redirects to `/{slug}` so the key doesn't linger in the address bar. Printed QR codes point to `/{slug}` (asks for the passcode) so they survive passcode changes.

**Who sees what** (`lib/server/site-view.js`)
- Two scopes: **invitation** (default public) and **memories** (default passcode).
- Phase picks the scope: `lib/phase.js` computes `invitation` (before the first event day) → `live` (event days + 1) → `memories` (after, once the couple publishes), in Asia/Dhaka time from ceremony start times. `phase_override` and the purchased products constrain it.
- Without memories access, only photos marked **public** are resolved (`publicOnly`), so a public invitation never exposes private photos. Couples/operators always see everything.
- The guestbook API follows the same rules.
- `PasscodeGate` (bilingual, uses the site's palette) is shown instead of the page when needed. Gallery lightbox shows a subtle “Shared with {name}” when the guest gave their name, and a transparent shield over the photo.

**Root URLs** — `src/app/s/[slug]` → `src/app/(site)/[slug]`; `/s/:path*` 308-redirects to `/:path*`; invalid slugs 404 without a database call; reserved words can't become slugs (Phase 1). Admin, dashboard and editor links updated.

**Couple / operator controls** — `GET|PATCH /api/sites/:id/access`, `POST /access/passcode` (generate or set own), `POST /access/revoke`. New editor panel **Privacy & sharing**: passcode with copy/new/custom, access per product, guestbook moderation, watermark on/off (re-renders existing photos with progress), site link, one-tap link, WhatsApp share text, QR code PNG for printed cards, sign everyone out.

## Database
No new migration (uses `site_access` from Phase 1).

## Environment (optional, recommended in production)
`GUEST_SESSION_SECRET`, `LINK_SIGNING_SECRET` (32+ chars each), `PASSCODE_ENC_KEY` (32 random bytes, base64). If unset they are derived from `SUPABASE_SERVICE_ROLE_KEY` (HKDF), which means rotating that key signs guests out and requires new passcodes.
